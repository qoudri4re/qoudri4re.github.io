SchoolOnline

A school management platform that replaces spreadsheets, fragmented tools, and paper records with a single system built for how Nigerian schools operate.

01 · Problem

The Context

Nigerian schools run on paper. Attendance, results, fee tracking, report cards: most schools still do these by hand. The ones that use software usually stitch together three or four tools that don't talk to each other. A teacher marks attendance in one spreadsheet, enters results in another app, and the bursar tracks fees in a separate system. Nobody has the full picture.

The school management platforms already in Nigeria are expensive, clunky, or built for a different era. Parent communication is a termly printed report card. A parent who wants to know whether their child attended school today, or what they owe in fees, has to call the school and wait for a manual lookup.

Legacy data

Schools switching from paper bring years of history: fee debts recorded in old ledgers, results from previous terms. The platform has to absorb this without forcing the school to re-enter everything or distort current fee structures to match old amounts.

02 · Requirements

What It Needed to Do

Core modules

  • Student records and class management
  • Attendance tracking with absenteeism alerts
  • Result computation with support for Nigerian grading scales
  • Report card generation with admin approval workflow
  • Fee tracking with multiple payment methods (Paystack, Flutterwave, bank transfer, cash)
  • Parent portal with real-time access to academic data and fee status

Business requirements

  • Schools pay based on what they use: base tier by student count, optional paid modules
  • Prorated mid-cycle upgrades, renewals that don't discard unused days, downgrades at cycle end
  • Calendar progression with strict readiness checks before advancing terms or academic years
  • Legacy debt onboarding: import historical fee debts without touching active fee structures

Non-functional requirements

  • Database-level tenant isolation (one database per school)
  • Real-time announcements and parent communication via Socket.io
  • Subscription enforcement at the middleware level with cached entitlement checks
  • Background jobs for analytics, fee reminders, and subscription lifecycle management

03 · Architecture

How I Approached It

The core architectural challenge was multi-tenant database routing. Each school gets its own PostgreSQL database. Isolating data at the database level means a school's information never mixes with another school's, and heavy queries from one school don't slow down anyone else. I wrote about the trade-offs behind this choice in more detail, comparing shared-schema, schema-per-tenant, and database-per-tenant, and why the last one fit this project.

Sequelize models store a static reference to their Sequelize instance. Without intervention, connecting School B's database would overwrite that reference and silently redirect all of School A's queries to School B's database.

Key architectural decision

The project uses Node's AsyncLocalStorage to bind the correct school database to each incoming request. Every Sequelize model's .sequelize property is patched at startup with a getter that reads from this async context instead of pointing to a static connection. A concurrent request for School B gets its own async chain pointing to School B's database.

Stack decisions

  • Angular for the frontend: strong typing with TypeScript, built-in dependency injection, and the structure it imposes on a large, module-heavy application.
  • Node.js + Express + TypeScript on the backend: RESTful web services with TypeScript for type safety and maintainability.
  • PostgreSQL with per-tenant databases: ACID-compliant transactions and strong data integrity for financial and academic records.
  • Redis: in-memory cache for frequently accessed data and token invalidation.
  • Socket.io: real-time communication for announcements, chat, and presence tracking over persistent, bidirectional connections.

04 · Implementation

Building It

The multi-tenant database routing was the first real technical hurdle. The AsyncLocalStorage getter pattern solved it cleanly, but it came with constraints. Background jobs, timeouts, event emitters, and anything that breaks out of the async chain lose the context and need an explicit runWithDb wrap.

The subscription system

The subscription system uses modular pricing: usage tiers, per-module pricing, dependency validation, prorated mid-cycle upgrades, and cached entitlement checks. A school on a cheaper plan can upgrade immediately and pays the prorated difference for the remaining time. Renewals don't discard unused days. Downgrades and lateral plan switches are blocked until the current cycle ends. Payment verification distinguishes initial purchases, renewals, and upgrades, and the webhook handlers make the same distinctions. The lifecycle job sends reminders and handles expirations without double-sending or missing a school.

Calendar progression

Calendar progression took iteration to get right. Moving a school from one term to the next, or rolling over an academic year, means results must be finalized, report cards created and admin-approved, and fee structures configured for the destination term. Year-end rollovers also need promotion decisions resolved for every student. The implementation runs these checks in a preview endpoint, then re-runs them inside a database transaction on confirm, so it never acts on a stale preview. The promotion placement logic (matching class arm names, checking capacity, handling graduation for final-year students) surfaced edge cases that weren't obvious during the initial design.

Legacy fee debt

The legacy fee debt feature exposed a tension between a clean ledger model and the reality of school onboarding. The original fee ledger assumed every debt came from a system-defined fee structure. Schools bring paper records with amounts that match no current fee configuration. The assignment model now supports multiple debt sources (legacy detailed, opening balance, manual adjustment) while keeping payment allocation unified across all of them. That required careful refactoring of the assignment status rules and the reporting queries.

Fee payment allocation

Manual payments, gateway payments, teller-verified payments, and webhook-processed payments flow through different code paths, but they all use the same FIFO strategy: oldest debt first. Centralizing that allocation in the payment service, and routing every payment entry point through it, was the important part. Without it, a gateway webhook could allocate differently from a manual payment, which is hard to catch and harder to explain to a bursar.

Socket.io in multi-tenant

Socket connections join rooms based on the user's role and the school they belong to. Subscription state can change mid-connection: a school's subscription expires, or modules get removed. The connection-level subscription gate runs once at handshake, and the entitlement cache has a short TTL, so a long-lived connection can outlive the cached access decision. Mid-connection re-authorization, or a forced disconnect on subscription expiry, is not implemented yet. The risk is a school keeping real-time access briefly after its subscription lapses.
